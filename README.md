# SIMD CPU — RTL to GDSII (Sky130 / OpenLane2)

A 16-bit SIMD processor taken end-to-end from Verilog RTL to a signed-off
GDSII layout on the SkyWater 130nm open PDK, plus a Python framework that
automates PPA (Power/Performance/Area) design-space exploration on top of
the physical design flow.

## Overview

- **Design**: 16-bit SIMD CPU — multi-cycle FSM (IF/ID/EX/MEM/WB) driving
  add/subtract, multiply, and shift units across three lane modes: 1×16-bit,
  2×8-bit, 4×4-bit.
- **Flow**: Yosys (synthesis) → OpenROAD (floorplan/place/CTS/route/STA) →
  Magic/KLayout/Netgen (DRC/LVS/GDS streamout), orchestrated by OpenLane2.
- **Target**: SkyWater Sky130 (`sky130_fd_sc_hd`), via the Nix-based
  OpenLane2 installation.

## Results (baseline run)

- ~4,100 standard-cell instances, 431 flip-flops
- Die area: ~369 × 380 µm
- **DRC: clean** · **LVS: clean** (circuits match, 0 device/net/pin mismatches)
- **Timing**: 0 setup/hold violations across all PVT corners at a 50ns clock
  (worst-case slack ~30ns — plenty of headroom to push the clock faster)
- Known open items: 1 antenna violation (1 net/1 pin), and slew/cap
  violations confined to the slow (`ss`) process corner — non-blocking for
  this scope, documented for anyone taking it further toward tapeout-grade
  signoff.

## Bug found and fixed

The original FSM's write-back stage only gated ADD/SUB results behind the
`STATE_WB` check; MUL/MAC/shift/AND/OR/NOT/SET/LOAD write-backs sat as
siblings of that check instead of nested inside it, so they could commit on
the wrong cycle. Fixed by nesting every write-back case under the same
`current_state == STATE_WB` condition — confirmed no inferred latches in
Yosys synthesis after the fix.

## Running the flow

Requires an OpenLane2 Nix installation and the Sky130 PDK via Volare.

```bash
nix-shell --pure ~/openlane2/shell.nix
cd simd_cpu
openlane --pdk sky130A config.json
```

GDS output lands at `runs/<tag>/final/gds/CPUtop.gds`.

Quick synthesis-only sanity check (faster than a full run):
```bash
yosys -s scripts/synth_check.ys
```

## PPA exploration framework

Instead of running the flow once, `sweep/` automates sweeping physical
design parameters (clock period, core utilization, placement density)
across multiple OpenLane runs, then extracts and visualizes the resulting
PPA tradeoffs.

```bash
cd sweep
python3 generate_configs.py     # build config variants
python3 run_sweep.py --workers 2   # run OpenLane for each (parallel-capable)
python3 parse_results.py        # extract metrics into results.csv
python3 visualize.py            # plot area/power vs. frequency
python3 pick_best.py --max-area 150000   # pick best config under a target
```

See `sweep/README.md` for full details on each script and the metrics
extracted.
